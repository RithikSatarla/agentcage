Open-source study · working code

Agents write to production. Their tests don’t.

The standard way to test an agent is to record an HTTP response and replay it. A replay fixture holds no state — so it cannot catch the one failure mode that only writes have.

Try it

Send the same refund twice

One charge for $50.00. Issue a refund, then issue it again — the way an agent does when it fails to parse the first response. The fixture column is what your test suite sees today.

charge ch_00000001 · $50.00 captured amount_refunded: $0.00
#Request Replay fixtureAgentCage
Refunded — against fixture $0.00
Refunded — against AgentCage $0.00

The fixture accepts every request, so it will cheerfully refund more than the charge was ever worth. The rules on the right mirror part_b/stripe_mock.py, which is the canonical implementation and the one covered by the test suite.

Why fixtures can't catch it

The defect lives in the state transition

POST /v1/refunds {"charge": "ch_00000001", "amount": 5000} replay fixture → 200 OK agentcage → 200 OK charge.amount_refunded 0 → 5000
POST /v1/refunds {"charge": "ch_00000001", "amount": 5000} ← the agent retries replay fixture → 200 OK suite passes. customer refunded twice. agentcage → 400 charge_already_refunded

Both requests are byte-identical. No assertion over a fixture's responses can separate them, because the fixture has nothing to remember. The suite is not incomplete — it is structurally incapable.

The bar was set as low as it goes. A tool counts as tested if its identifier appears anywhere in the project's test sources — no assertion, no destructive path exercised, not even executed. One in five fails that. So 20.3% is a floor, not a ceiling.

Breakdown

Version-control and shell tools are the least tested

Pooling every write into one number hides the useful question: which dangerous operations are the untested ones. Each detected tool carries the categories that qualified it, so coverage breaks down by the kind of side effect it has.

Version-control writes — tools that open pull requests, push commits, or write files into a repository — are the least covered at 46.7% never referenced. Shell execution follows at 33.3% of 36 tools, and it has the least bounded blast radius of any category, since a shell tool can produce every other category's effects. Filesystem and database writes are comparatively well covered.

Read the intervals, not the ordering. Several categories hold fewer than 20 tools and their confidence intervals overlap heavily. The claim is only that the extremes separate: version-control and shell tools are less covered than database and filesystem tools. Categories also overlap — a tool may match several — so the counts do not sum to 158.

Coverage is not uniform: 84.4% of all untested tools sit in three repositories, each shipping a large tool catalogue. The pooled figure describes the ecosystem's tool population rather than a typical project.

What this does not say. The study detects framework-idiomatic tool definitions — @tool, BaseTool, JSON tool schemas. 32 of the 45 candidates screened out, including agents like aider and OpenHands that write to disk constantly but expose no such surface. The denominator of 13 reflects detector coverage as much as it reflects the ecosystem. Part A is exploratory, not pre-registered, and the protocol lists all seven detector revisions — including two that made this finding weaker.

The mechanism

State, not recordings

A model where writes mutate state and later reads observe the mutation.

from part_b.stripe_mock import StripeMock

stripe = StripeMock()
charge = stripe.post_charge(amount=5000, currency="usd")

stripe.post_refund(charge=charge.id, amount=5000)
stripe.get_charge(charge.id).amount_refunded   # 5000  ← the read sees the write

stripe.post_refund(charge=charge.id, amount=5000)
# StripeError: Charge ch_00000001 has already been refunded.
#              (400 charge_already_refunded)

Capture is passive. It attaches through each HTTP library's own documented hook points and never rewrites a request, injects a response, or short-circuits the transport — a test asserts the caller receives exactly what the transport returned.

import httpx
from part_b.interceptor import Interceptor

cage = Interceptor()
client = httpx.Client(event_hooks=cage.httpx_event_hooks())

run_my_agent(client)

for trace in cage.writes:          # POST / PUT / PATCH / DELETE
    print(trace.method, trace.path, trace.status_code)

Credential headers are redacted at capture time, so traces are safe to commit.

The study costs 45 GitHub API calls, inside the unauthenticated hourly limit. It re-runs weekly in CI, and every push re-runs the pipeline against the live API. Every figure on this page and in the paper is generated from part_a/results.json — a test fails the build if any of them drift.

Design partners

Looking for teams running agents that write

The Stripe model is the first of many. Which API gets built next, and what fidelity it needs, should be decided by teams with a real agent in production rather than guessed.

What you get

  • A stateful model of the API your agent writes to, built to your failure cases
  • Direct input on the interceptor and test-harness design
  • Your write paths exercised against real state transitions before they ship
  • MIT licensed — no lock-in, and it keeps working if we go away

What we need back

  • Which API, and which operations actually scare you
  • The failure modes you have already hit in production
  • Honest feedback on whether this catches anything real

No pricing, no contract, no beta waitlist. The code is public and the study is reproducible — start by running it and telling us where it is wrong.
