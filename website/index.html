Agents write to production. Their tests don’t.

The standard way to test an agent is to record an HTTP response and replay it. A replay fixture holds no state — so it cannot catch the one failure mode that only writes have.

POST /v1/refunds {"charge": "ch_00000001", "amount": 5000} replay fixture → 200 OK agentcage → 200 OK charge.amount_refunded 0 → 5000
POST /v1/refunds {"charge": "ch_00000001", "amount": 5000} ← the agent retries replay fixture → 200 OK suite passes. customer refunded twice. agentcage → 400 charge_already_refunded

Both requests are byte-identical. Only a mock that holds state can answer them differently — which is exactly what the correct answer requires.

The measurement

How much of this is actually tested?

We screened 45 Python agent repositories, mechanically extracted every framework-idiomatic tool definition, and kept the ones whose bodies perform a real state mutation.

20.3%

of write-capable tool definitions in open-source LLM agents are never referenced by any test — 32 of 158, across 13 repositories.

The bar was set as low as it goes. A tool counts as tested if its identifier appears anywhere in the project’s test sources — no assertion, no destructive path exercised, not even executed. One in five fails that. So 20.3% is a floor, not a ceiling.

Restricting to the 7 repositories whose entire test suite was read gives 20.7%. The result is not an artefact of sampling.

What this does not say. The detectors find framework-idiomatic tool definitions — @tool, BaseTool, JSON tool schemas. 32 of the 45 candidates screened out, including agents like aider and OpenHands that write to disk and shell out constantly but expose no such surface. The denominator of 13 reflects detector coverage as much as it reflects the ecosystem. Part A is exploratory, not pre-registered, and the protocol lists all seven detector revisions — including two that made this finding weaker.

The mechanism

State, not recordings

A model where writes mutate state and later reads observe the mutation.

from part_b.stripe_mock import StripeMock

stripe = StripeMock()
charge = stripe.post_charge(amount=5000, currency="usd")

stripe.post_refund(charge=charge.id, amount=5000)
stripe.get_charge(charge.id).amount_refunded   # 5000  ← the read sees the write

stripe.post_refund(charge=charge.id, amount=5000)
# StripeError: Charge ch_00000001 has already been refunded.
#              (400 charge_already_refunded)

Capture is passive. It attaches through each HTTP library’s own documented hook points and never rewrites a request, injects a response, or short-circuits the transport — a test asserts the caller receives exactly what the transport returned.

import httpx
from part_b.interceptor import Interceptor

cage = Interceptor()
client = httpx.Client(event_hooks=cage.httpx_event_hooks())

run_my_agent(client)

for trace in cage.writes:          # POST / PUT / PATCH / DELETE
    print(trace.method, trace.path, trace.status_code)

Credential headers are redacted at capture time, so traces are safe to commit.

The study costs 45 GitHub API calls, which fits inside the unauthenticated hourly limit. It re-runs weekly in CI, and every push re-runs the pipeline against the live API to prove it still works. Every figure on this page, in the README, and in the paper is generated from part_a/results.json — a test fails the build if any of them drift.

The paper

Untested by Construction

Test Coverage of Write-Capable Tools in Open-Source LLM Agents. Seven pages. Method, full per-repository results, the detector revision history, and threats to validity — including the screening rate that bounds what the headline means.

The paper’s numbers are generated from the results file rather than typed, so it cannot drift from the data. Part B’s evaluation is pre-registered in it: hypothesis, four defect classes, and an explicit falsification threshold, all written down before the experiment runs.

Design partners

Looking for teams running agents that write

The Stripe model is the first of many. Which API gets built next, and what fidelity it needs, should be decided by teams with a real agent in production rather than guessed.

What you get

  • A stateful model of the API your agent writes to, built to your failure cases
  • Direct input on the interceptor and test-harness design
  • Your write paths exercised against real state transitions before they ship
  • MIT licensed — no lock-in, and it keeps working if we go away

What we need back

  • Which API, and which operations actually scare you
  • The failure modes you have already hit in production
  • Honest feedback on whether this catches anything real

No pricing, no contract, no beta waitlist. The code is public and the study is reproducible — start by running it and telling us where it is wrong.
