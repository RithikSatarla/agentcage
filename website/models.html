What these models claim, and what they don’t.

Modelled

  • A refund moves amount_refunded, and the next read observes it
  • A second refund on a fully refunded charge is refused
  • A refund larger than the unrefunded remainder is refused
  • An uncaptured charge cannot be refunded at all
  • Idempotency keys replay the first answer instead of acting twice
  • File contents are keyed by branch, so a sha read on one is stale on another
  • Issue creation has no idempotency key, so a retry really does make two

Not modelled

  • Disputes, payouts, webhooks, 3-D Secure, connected accounts
  • Pagination and rate limits
  • Anything requiring a real account’s pre-existing state
  • Forks complete synchronously here; the real endpoint is asynchronous
  • JQL beyond equality on project and status

The models were built against the three agents in the study, adding endpoints as runs reached them. That is why the miss rate in Part B is zero and why that number says more about fit than about coverage of an agent we have not seen. The full caveat is on the explainer.

what it remembers

Every rule here is enforced by part_b/stripe_mock.py and asserted by the test suite. Refund more than is left, or refund twice, and it refuses with the error the real API sends.

Two pieces

1

It watches

Attaches to your existing httpx or requests client and records every call. It never rewrites a request or fakes a reply — a test asserts your agent gets the response back byte for byte.

API keys stripped before anything is written down
2

It remembers

A refund changes the charge, and every later read sees the change. Identifiers come from a counter and the clock is injectable, so the same run gives the same result every time.
